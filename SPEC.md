## 1. Цель

Приложение с REST API для работы с кошельками: изменить баланс (DEPOSIT/WITHDRAW), получить баланс.
Проверяется реальный уровень Python-разработки, поэтому ценится не объём кода, а корректность в
конкурентной среде, миграции, тесты и воспроизводимый запуск одной командой.

## 2. Не входит в объём (non-goals)

- Пользователи, аутентификация, авторизация: в задании их нет, кошелёк адресуется по UUID.
- Перевод между кошельками, история операций, лимиты, идемпотентность по ключу запроса.
- UI, админка, метрики Prometheus, трассировка.
- Деплой на сервер: задание просит решение на GitHub со ссылкой.
- Мультивалютность: одна валюта, поле валюты не вводим, чтобы не плодить сущности без требования.

## 3. Функциональные требования

- **FR-1** `POST /api/v1/wallets/{wallet_uuid}/operation` принимает `operation_type` (`DEPOSIT`|`WITHDRAW`)
  и `amount`, применяет операцию к балансу кошелька и возвращает новый баланс.
- **FR-2** `GET /api/v1/wallets/{wallet_uuid}` возвращает текущий баланс.
- **FR-3** Кошелёк адресуется UUID, который приходит в пути. Кошелёк, которого нет в БД, — это `404`
  (см. §10.1: автосоздание при DEPOSIT — открытый вопрос, по умолчанию выключено).
- **FR-4** Валидация входа: `amount > 0` и не более 2 знаков после точки; `operation_type` — только два
  значения из задания; `wallet_uuid` — валидный UUID. Всё остальное — `422`.
- **FR-5** Баланс не может стать отрицательным ни при каком сценарии, включая конкурентный.
  Инвариант подтверждается на уровне БД: `CHECK (balance >= 0)`.
- **FR-6** `GET /health/live` — процесс жив (без обращения к БД); `GET /health/ready` — БД отвечает
  (`503`, если нет).
- **FR-7** `python -m scripts.seed --count N` создаёт N кошельков и печатает их UUID с готовой
  curl-последовательностью — чтобы проверяющий увидел сценарий за минуту, не заходя в psql.

## 4. Конкурентность (ключевое требование задания)

Инварианты, которые обязаны держаться при одновременных запросах по **одному и тому же** кошельку:

- **INV-1** N параллельных `DEPOSIT` на суммы S₁…Sₙ: итоговый баланс = стартовый + ΣSᵢ, ровно.
  Ни одно обновление не теряется (нет lost update).
- **INV-2** M параллельных `WITHDRAW`: успешных ровно столько, сколько вмещает баланс; все
  остальные — `409`; баланс никогда не уходит в минус.
- **INV-3** Инварианты держатся независимо от числа процессов uvicorn и от того, один клиент
  работает или параллельные. Значит, атомарность обеспечивается в БД, а не в памяти процесса.

Допустимые механизмы (любой из двух, выбор реализации — свободный):

- **(a)** транзакция + блокировка строки: `SELECT … FOR UPDATE`, изменение в Python, `COMMIT`;
- **(b)** один атомарный `UPDATE`: `UPDATE wallets SET balance = balance + :delta WHERE id = :id` для
  депозита и `… AND balance + :delta >= 0` для списания с проверкой `rowcount`.

**Недопустимо:** «прочитал в Python → посчитал → записал» без блокировки строки и без условия в
`WHERE` (классический read-modify-write). Такой код проходит тесты на низкой нагрузке и теряет
деньги под параллельными запросами — это ровно то, что проверяет задание.

## 5. Контракты

### Изменение баланса

```
POST /api/v1/wallets/{wallet_uuid}/operation
{"operation_type": "DEPOSIT" | "WITHDRAW", "amount": 1000}
```

`200`:

```json
{"wallet_id": "3f2b…", "operation_type": "DEPOSIT", "amount": "1000.00", "balance": "1000.00"}
```

### Получение баланса

```
GET /api/v1/wallets/{wallet_uuid}
```

`200`:

```json
{"wallet_id": "3f2b…", "balance": "700.00"}
```

Деньги в JSON — **строки** (`"1000.00"`), а не числа: `Decimal` не теряет точность, а JSON-число
превращается у клиента в `float`. Имя поля — `balance` в обоих ответах, чтобы клиент читал баланс
одинаково из обоих эндпоинтов.

| Ситуация | Код | Тело |
|---|---|---|
| Кошелька с таким UUID нет | `404` | `{"detail": "wallet not found"}` |
| Снятие больше баланса | `409` | `{"detail": "insufficient funds"}` |
| `amount ≤ 0` или > 2 знаков, неизвестный `operation_type` | `422` | стандартное тело FastAPI |
| `wallet_uuid` — не UUID | `422` | стандартное тело FastAPI |

## 6. Нефункциональные требования

- **NFR-1** PEP8: `ruff check .` и `ruff format --check .` — оба exit 0 (конфиг в `pyproject.toml`).
- **NFR-2** Миграции: `alembic upgrade head` на пустой БД создаёт схему; `alembic downgrade base`
  её убирает; повторный `upgrade head` проходит. Схема создаётся **только** миграцией, не `create_all`.
- **NFR-3** Инфраструктура: `docker compose up --build` поднимает API и PostgreSQL; миграции
  применяются автоматически перед стартом API; порты наружу — только `127.0.0.1`.
- **NFR-4** Эндпоинты покрыты тестами (`pytest`), включая конкурентные сценарии INV-1/INV-2.
- **NFR-5** Python ≥ 3.11 (в контейнере 3.12), зависимости с верхними границами версий.

## 7. Критерии приёмки

| AC | Проверка | Оракул (чем доказывается) |
|---|---|---|
| AC-1 | `GET` существующего кошелька возвращает его баланс из БД | `tests/test_wallets.py::test_get_balance_returns_stored_value` + `SELECT balance` в psql |
| AC-2 | `DEPOSIT` увеличивает баланс на сумму | `test_deposit_increases_balance` |
| AC-3 | `WITHDRAW` уменьшает баланс; снятие больше баланса → `409` и баланс не меняется | `test_withdraw_decreases_balance`, `test_withdraw_more_than_balance_is_rejected` |
| AC-4 | `404` по неизвестному UUID (оба эндпоинта), `422` на невалидный вход | `test_unknown_wallet_*`, `test_validation_errors` (параметризован) |
| AC-5 | 50 параллельных `DEPOSIT` по 10 на один кошелёк → баланс `"500.00"` ровно | `test_concurrent_deposits_lose_no_updates` |
| AC-6 | 20 параллельных `WITHDRAW` по 100 при балансе 1000 → ровно 10×`200`, 10×`409`, баланс `"0.00"` | `test_concurrent_withdrawals_do_not_overdraw` |
| AC-7 | Миграции вверх/вниз/вверх проходят на пустой БД | команды из NFR-2 в контейнере `app` |
| AC-8 | `docker compose up --build` из чистого состояния: оба контейнера healthy, curl-последовательность из README даёт ожидаемые ответы | `docker compose ps` + вывод curl |
| AC-9 | Весь набор тестов зелёный | `pytest -q`, число тестов называется точным |
| AC-10 | Линтер чистый | `ruff check .`, `ruff format --check .` — exit 0 |

## 10. Открытые вопросы (твои решения)

1. **Кошелёк по неизвестному UUID при `DEPOSIT`** — `404` (сейчас) или автосоздание с нулевым
   балансом? Автосоздание удобнее проверяющему (достаточно curl), но превращает опечатку в новый
   кошелёк. По умолчанию — `404` + `scripts/seed.py`.
2. **Недостаточно средств** — `409` (сейчас) или `400`? Оба защищаемы; `409` точнее описывает
   «конфликт с текущим состоянием ресурса».
3. **Тесты на хосте или в контейнере** — README предлагает оба варианта; если хочется короче, оставить
   только контейнерный (проверяющему он ближе к тому, как он будет запускать).
4. **ADR** — писать ли 2–3 коротких ADR (Postgres + async SQLAlchemy; механизм конкурентности; тип
   денег) в `docs/adr/`. В задании не требуется, но для ревью «как на проекте» это сильный артефакт.

## 11. Риски

- **Docker Desktop** держит 1–2 ГБ резидентной памяти; прогон AC-8 требует закрыть лишние программы.
  Прогон миграций и тестов при поднятом контейнере `db` — единственный обязательный контейнерный шаг.
- Базовый образ `python:3.12-slim` и `postgres:16-alpine` скачиваются при первой сборке (нужна сеть).
- **На машине уже работает локальный PostgreSQL 18 на порту 5432**, поэтому контейнер `db` публикует
  `55432` (иначе compose не сможет занять порт). Внутри сети compose база доступна как `db:5432`.
  Побочный эффект: повседневный цикл можно вести вообще без Docker, на локальной базе.
